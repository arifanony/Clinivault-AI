PROJECT BRIEF: PRODUCTION-ORIENTED HEALTHCARE RAG SYSTEM

1. PROJECT GOAL

I want to build a production-oriented Healthcare RAG application as a standalone product.

This should not be a toy chatbot that simply uploads one PDF and answers questions.

The system should demonstrate how a real-world RAG application can be designed with:
- robust document ingestion
- structured document metadata
- scalable retrieval
- evidence-backed answers
- citations and provenance
- observability
- evaluation readiness
- production deployment capability

The initial domain is healthcare, but the architecture should avoid unnecessary hard-coding where possible.

The Healthcare RAG and the separate project called Errata are two independent products.

This repository is only for the Healthcare RAG.

Errata will later integrate with this RAG as an external evaluation harness through a shared structured data contract.

DOCUMENT INGESTION
    ↓

    ↓

    ↓

    ↓

    ↓

    ↓

    ↓
RETRIEVAL LAYER
    ↓

    ↓

The first goal is to make this entire pipeline work correctly end-to-end.


3. DOCUMENT INGESTION PIPELINE

The ingestion pipeline is important.

We should support ingestion of multiple healthcare documents rather than building the MVP around a single PDF.

The initial pipeline should be:

PDF
 ↓
Parse
 ↓
Extract text + structure
 ↓
Clean / normalize
 ↓
Attach document metadata
 ↓
Chunk
 ↓
Attach chunk metadata
 ↓
Generate embeddings
 ↓
Store vectors + metadata

Metadata should include where available:
- document_id
- document_name
- source
- page_number
- section
- chunk_id
- publication_date
- ingestion_date
- document_version
- parser_status

The vector database should store:
- embedding
- chunk_text
- metadata

Metadata must remain retrievable together with the chunk.


4. INGESTION EVIDENCE

The system should generate structured ingestion information.

Example:

{
  "document_id": "...",
  "total_pages": 100,
  "parsed_pages": 100,
  "failed_pages": [],
  "total_chunks": 850,
  "embedded_chunks": 850,
  "indexed_chunks": 850,
  "ingestion_status": "success"
}

This is important because later the external Errata product may evaluate ingestion quality.

The RAG itself should produce evidence.

It should not contain Errata evaluation logic.


5. RETRIEVAL

The initial retrieval system should be reliable but not unnecessarily complex.

Start with:

User Query
   ↓
Embedding
   ↓
Vector Search
   ↓
Top K Chunks

Each retrieved result should preserve:
- chunk_id
- document_id
- document_name
- page_number
- section
- similarity_score
- chunk_text

The goal is to make retrieval traceable.

If the system gives an answer, we should be able to inspect exactly which evidence was retrieved.


6. CONTEXT CONSTRUCTION

Retrieved chunks should not simply be dumped blindly into the prompt.

Create a dedicated context-building layer.

Responsibilities:
- select retrieved chunks
- preserve ordering
- respect context limits
- preserve source metadata
- prepare evidence for the LLM

The LLM should receive evidence in a structured and traceable form.


7. ANSWER GENERATION

The answer generation layer should use retrieved evidence.

The system should aim to:
- answer based on retrieved context
- avoid unsupported claims
- clearly indicate when evidence is insufficient
- support abstention when necessary
- provide source references

Example behavior:

Question
   ↓
Retrieve evidence
   ↓
Is sufficient evidence available?
   ├── Yes → Generate evidence-backed answer
   └── No → Abstain / indicate insufficient information


8. CITATIONS AND PROVENANCE

Every answer should be traceable.

The response should ideally contain references such as:

Source:
Document: Clinical Guidelines XYZ
Page: 24
Section: Treatment Recommendations

The system should preserve provenance from ingestion through retrieval to generation.

This is important for healthcare and also for future evaluation.


9. STRUCTURED RAG EXECUTION RECORD

For every query, the system should generate a structured execution record.

This is a key architectural requirement.

Example:

{
  "run_id": "...",
  "timestamp": "...",
  "query": "...",
  "retrieval": {
    "top_k": 5,
    "chunks": [
      {
        "chunk_id": "...",
        "document_id": "...",
        "page_number": 10,
        "score": 0.82
      }
    ]
  },
  "context": {
    "chunk_ids_used": []
  },
  "generation": {
    "model": "...",
    "answer": "...",
    "abstained": false
  },
  "sources": []
}

The exact schema can evolve.

The important thing is that the RAG produces structured evidence about its own execution.

Later, Errata should be able to consume these records.


10. INITIAL TECHNOLOGY DIRECTION

The implementation should be modular so components can later be replaced.

Potential components include:
- Python
- FastAPI
- Streamlit for MVP UI
- Document parser
- Embedding model
- Qdrant vector database
- LLM provider/model
- Docker

Do not tightly couple the architecture to one framework.


11. ARCHITECTURE PRINCIPLES

Separation of concerns

Separate:
- ingestion
- retrieval
- context building
- generation
- citations
- logging
- API/UI

Replaceable components

The following should be replaceable without rewriting the entire system:
- parser
- embedding model
- vector database
- LLM
- retrieval strategy

Evidence first

The system should preserve evidence and metadata rather than only producing a final answer.

No unnecessary complexity initially

Do not add:
- agents
- multi-agent systems
- complicated orchestration
- expensive semantic chunking
- AI judges everywhere

unless there is a clear reason.

Start with deterministic and observable components.


12. PROJECT PHASES

PHASE 1 — BASELINE RAG

Build:
- Document ingestion
- Chunking
- Embedding
- Vector storage
- Retrieval
- LLM answer generation
- Citations
- Structured execution logging

Success criteria:

A user can ask a question and we can inspect:

question
↓
retrieved chunks
↓
retrieval scores
↓
context used
↓
generated answer
↓
sources


PHASE 2 — STRENGTHEN INGESTION

Improve ingestion with:
- multi-document ingestion
- metadata extraction
- page-level tracking
- parse status
- chunk statistics
- embedding/index validation
- ingestion report

Start with a meaningful number of healthcare documents rather than a single toy document.

However, scale incrementally.


PHASE 3 — IMPROVE RETRIEVAL

Only after baseline measurements exist, consider:
- metadata filtering
- better retrieval strategies
- hybrid retrieval
- reranking
- query improvements

Do not add these automatically.

Each improvement should have a reason and measurable benefit.


PHASE 4 — ANSWER RELIABILITY

Improve:
- abstention
- citation handling
- context quality
- unsupported-answer prevention


PHASE 5 — PRODUCTIONIZATION

Later:
- FastAPI production API
- Docker
- environment configuration
- logging
- observability
- tests
- CI/CD
- deployment

This is not the first MVP target.

14. RELATIONSHIP WITH ERRATA

Important:

Errata is not part of this product.

Errata is a separate universal AI evaluation harness.

This Healthcare RAG will later act as one real integration/use case.

The integration boundary should be:

Healthcare RAG
       │
       │ Structured evidence / execution records
       ▼
     Errata
       │
       ├── Ingestion evaluation
       ├── Retrieval evaluation
       ├── Generation evaluation
       ├── Risk analysis
       └── Evaluation reports

Do not implement Errata inside this repository.

Only ensure the RAG produces clean, structured, traceable evidence that an external evaluator can consume.
