# Engineering Log: Local Multi-Model Embedding Evaluation Expansion (EVAL-HF-002)

- **Date:** 2026-09-22
- **Task:** EVAL-HF-002
- **Author:** Coding Agent

## Objective
Identify whether alternative model lineage architectures (e.g. GTE, E5, Micro variants) consistently outperform the previously verified local baseline configurations (MiniLM, BGE) when evaluated strictly against the frozen 46-case extraction benchmark under local execution constraints.

## Methodology
- Genesis task `EVAL-HF-002` activated.
- Evaluated 3 distinct additional architectures:
  - `thenlper/gte-small` (General Text Embeddings Lineage)
  - `intfloat/e5-small-v2` (Microsoft E5 Lineage)
  - `TaylorAI/bge-micro-v2` (Miniaturized 17M parameter network)
- Passed `local_files_only=True` to the execution pipeline to circumvent intense rate limiting and `ReadTimeoutError` stalls issued by Hugging Face's unauthenticated hub when querying repository hashes sequentially on constrained environments.
- Extracted and computed identical matrix tests.

## Findings

### FACT
- **Performance Thresholding**: `intfloat/e5-small-v2` achieved a maximum MRR of **0.5583**, slightly displacing the previous champion `BAAI/bge-small-en-v1.5` (MRR **0.5428**) tested in EVAL-HF-001.
- **Micro-Scale Architecture Efficacy**: Even extreme miniaturizations like `TaylorAI/bge-micro-v2` (MRR 0.4518) managed to vastly beat the hashing baseline (MRR 0.3601) and outperformed standard configurations like `all-MiniLM-L6-v2` (MRR 0.4105) despite shrinking overall size by 60%.
- **Zero-Shot Binding Execution**: E5 models normally mandate `query:` / `passage:` prefixes directly inside input prompts, but the test implemented a raw zero-shot wrapper inside `HFEmbeddingProvider`. Regardless, E5-small successfully proved extremely potent even when zero-shot evaluated.

### INFERENCE
- **API and Architecture Limitations**: Expanding to larger architectures natively on edge clusters incurs diminishing returns (e.g. 768 parameters degrades latency 3x with worse/equal retrieval context scaling). Models structurally optimized under 384 parameters provide the best possible index stability for our medical domain context.
- **Provider Choice Strategy**: Microsoft E5 architecture sits firmly as the best candidate structure for standard medical ontology dense extraction locally.

### NOT-YET-VALIDATED
- **Implementation Trade-offs**: Adopting the Microsoft E5 semantic paradigm into the production Retrieval Core engine requires structural rewriting to replace Lexical hash mapping and introduces PyTorch dependencies into standard production packaging.
